# ScanMark demo-asset package

Product screenshots and screen recordings of the **real ScanMark application**, captured by Playwright for a 30-second launch film. Nothing in the image and video assets is a mock-up. Each one comes from the Flask app in `ScanMark/` (commit `2e5e488`), booted locally with its own Procfile command against an isolated, fictional dataset. Every figure on screen was checked against the database it came from (see `verification.json`).

- **Shot list for the film:** [`SHOT_LIST.md`](SHOT_LIST.md)
- **Proof the figures are right:** [`verification.json`](verification.json) (checks against the database) and [`capture-log.json`](capture-log.json) (what was on screen at each still, plus a timestamped event log)
- **Rebuild everything:** [`tooling/run_demo.sh`](tooling/run_demo.sh)

**Resolution.** Desktop stills use a **1920×1080 CSS viewport at 2× device scale**, so they are 4K: room to push in, rotate and place the UI in 3D without softening. They're taken from a second, unrecorded tab in the same signed-in session, opened at the same moment as the recording, so the recorded window never jumps. The desktop recording itself renders at 1× (native 1920×1080). The phone is a **390×844 CSS window at a real 3× device scale**, the size of a typical modern Android phone, so its stills *and* its recording are 1170×2532.

**Frame rate.** The capture container has no GPU, and the app's glass and backdrop-blur styling is expensive to software-render. Static holds and the scanner overlay are clean. Scrolls and page transitions sample at roughly **12–15 distinct frames per second** inside the 30 fps files. For a hero scroll, use the tall stills (`05b`, `06b`) with a camera move in post; that's perfectly smooth and just as authentic. The phone recording ends on the portal rather than scrolling it, and `07` frames the records row directly.

The recordings contain no cursor, browser chrome, dev tools, test-runner overlays or dialogs. The only native dialog in the flow is the "End class?" confirm; it was accepted programmatically and never rendered. Pacing is deliberate: key screens hold for 2.5–4 s. The real page timing is preserved, and frames are re-timed to a constant 30 fps.

## What was demonstrated, end to end

1. **The lecturer opens a class.** Dr. Amara Okafor picks the saved classroom on the CSC 201 card and presses **Start Attendance**, through the real dashboard form. The server opens a class session, freezes a 24-student roster snapshot and pins the session to *Lecture Theatre 2*.
2. **The projector shows the live QR.** It's an HMAC-signed token that the page refreshes every 12 s ("Code refreshes in Ns").
3. **Classmates check in.** Nineteen fictional classmates each sign in with their own account and post to the real **`/mark_attendance`** endpoint. Each post carries the token the projector shows at that moment, a CSRF token, and a GPS fix inside the classroom's 60 m geofence. The projector's live roll call fills in by itself.
4. **The featured student scans with the phone.** Tolu Adeyemi opens **Start Camera & Scan → Start Advanced Scanner**. The app's own `static/scanner.js` opens the camera, its jsQR decoder reads the projector's code, and it gets a GPS fix and posts the scan. ScanMark checks the signature, token age, session state, enrolment and geofence, and answers `200 success`. The token the phone decoded was the live session's own (`S19`, confirmed in `capture-log.json`).
5. **The arrival appears on the projector.** Tolu Adeyemi lands at the top of "Present Today" at 15 / 24.
6. **The lecturer ends the class.** Five late classmates arrive first, then **End Class & Close Attendance**. The server closes the session, and the register shows 20 / 24 (83%) with the featured student in the sheet.
7. **Analytics.** The real course analytics page plots present-per-session across all nine meetings, today's included.

### How the camera works (read before editing beat 3)

The demo runs in a headless browser with no physical camera, and **no desktop browser was passed off as having scanned a physical QR code.** The phone instead uses Chromium's **fake video-capture device**, fed with a still taken from the lecturer's projector page seconds before the scan: the real card with the real, live QR. Everything downstream is the production code path: `getUserMedia` → `scanner.js` → jsQR → `fetch('/mark_attendance')` → the app's service worker → the server. The viewfinder, status pill and success banner are the app's own.

Consequences:
- The feed is a clean still on a dark surround, not a handheld shot of a real screen. The scanner's distance-hunting behaviour (digital zoom, exposure and torch escalation) was not needed and was not exercised.
- The phone's GPS is Playwright's geolocation emulation, 18 m from the room's pinned centre at ±9 m. Chromium stamps an emulated fix with the moment it was set, so the script refreshes it while the scanner is open, as a phone's GPS would. Without that, the app correctly rejected the minute-old fix as stale (this was the first attempt's failure).
- The scan request was **held for about 1.7 s** by Playwright, purely so the in-flight "Marking attendance..." screen could be photographed for `03`. It was then sent unmodified. The video keeps that pause.

### Things the footage shows that the editor should know

- **`04`: the records table under the success banner still reads 7.** The scan page renders that table on load and doesn't refresh it after a scan; that's how the app behaves today. The portal (`07`) shows the updated 8 / 9. Crop to the banner, or cut to `07`, if the stale 7 would confuse.
- **`07` and the portal in `08`: cards touch the screen edges.** The app's `.page-wrap` rule (`ScanMark/static/style.css:534`) removes Bootstrap's side gutter on phones. It's a real rendering issue, left as is.
- **`03`: the small "1280x720" text half-hidden behind the status pill** is the scanner's own camera-info label.
- **Today's scan times all fall within about 90 seconds** (02:22–02:23 PM in this run), because the capture compresses a lecture's arrivals for filming. Past lectures' scan times spread across their first 17 minutes.
- **Times are shown in Africa/Lagos** (the app's default `SCANMARK_TIMEZONE`).

## The demo environment

| Part | Setting | Why |
|---|---|---|
| App | `ScanMark/` at `2e5e488`, unmodified, run with `gunicorn --config gunicorn.conf.py app:app` (the Procfile command), 2 workers | the real product, as deployed |
| Mode | `SCANMARK_ENV=development` | local HTTP, so cookies are not `Secure`-only. Email verification is off by default here; the seeded accounts are marked verified |
| Database | a fresh SQLite file in a temporary run directory, deleted and re-seeded on every run | isolated; the seed script **refuses** any non-SQLite URL, any non-development environment, or a database that already holds users |
| Redis | a private `redis-server` on its own port, `--save ''`, shut down afterwards | sessions, QR tokens and rate limits, as in production |
| Mail | pointed at a closed local port | nothing leaves the machine |
| Secrets | a random `SECRET_KEY` and a random shared demo password, generated per run and kept in the run directory | not in this package; `verification.json` confirms neither string appears in any file here |
| Network | the app on `127.0.0.1` only. The browser fetched only the app's public CDN assets (Bootstrap, Font Awesome, Poppins, Chart.js) | — |

Production was not touched, and no deployed URL was opened.

**Differences from production:** SQLite instead of Postgres (the app prints its own warning about this) and development cookies over HTTP. The geofence (`GEOFENCE_REQUIRED`, on by default) and the signed, expiring QR tokens behaved exactly as shipped.

## Reproducing the captures

Requirements: Python 3.11+, Node 18+, `redis-server`, `ffmpeg` (with `libvpx-vp9` and `libx264`), and Playwright's Chromium.

```bash
python3 -m venv .venv && .venv/bin/pip install -r ScanMark/requirements.txt
npm install --prefix artifacts/scanmark-demo/tooling      # playwright 1.56.1
npx --prefix artifacts/scanmark-demo/tooling playwright install chromium

PYTHON=.venv/bin/python bash artifacts/scanmark-demo/tooling/run_demo.sh
```

The run takes about four and a half minutes, most of it encoding. It rewrites every asset in this folder, then `verification.json`, and exits non-zero if any check fails. Optional variables: `DEMO_RUN_DIR`, `DEMO_PORT` (8100) and `DEMO_REDIS_PORT` (6391). Behind an HTTPS-only egress proxy the script passes `HTTPS_PROXY` to Chromium and keeps the local app off it.

Dates come out relative to the day you run it (the live lecture is "today"; past lectures are the preceding Mondays and Wednesdays), and the attendance draws are seeded, so headcounts and percentages repeat.

| Tool | Does |
|---|---|
| `tooling/run_demo.sh` | Owns the whole lifecycle: private Redis, secrets, seed, boot, capture, verify, teardown |
| `tooling/seed_demo.py` | Writes the fictional dataset; refuses anything but a fresh local SQLite file |
| `tooling/capture_demo.cjs` | The Playwright run: both browsers, the camera feed, the recorders, the stills |
| `tooling/package.json` | Pins `playwright@1.56.1` |
| `tooling/verify_demo.py` | Recomputes every on-screen figure from SQLite, checks files and decodes, scans for leaked secrets |
| `tooling/timeline.py` | Prints the in-point tables above from `capture-log.json` |

## Not captured

These features exist in ScanMark but aren't in this package: the CSV register's contents, the audit-trail page, the classrooms page, HOD/Dean/DAP dashboards, CampOS SSO, Event Check-In Mode, signup and password reset. The register's **CSV** and **Audit Trail** buttons are visible in `05`; their pages weren't opened. Nothing in the film should depict them beyond those buttons without a new capture.
